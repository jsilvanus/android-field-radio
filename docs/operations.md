# android-field-radio: Operations & Deployment Guide

**Version:** 1.0 (2026-11-13)  
**Audience:** VPS operator, church IT staff

---

## Overview

This guide covers:
1. **SSH user setup** for phone broadcasts (`radiopub` user, restricted keys)
2. **Invite code management** (create, revoke, lifecycle)
3. **Monitoring** (stream status, logs, bandwidth)
4. **Troubleshooting** (connection drops, duplicate streams, auth failures)
5. **Scaling** (multi-stream, credential refresh, session cleanup)

- VPS running web-radio-relay (existing)

- field-radio-control service deployed (post-MVP; MVP can use manual credential minting)
- MediaMTX deployed on VPS (planned; MVP uses loopback nginx-rtmp only)

## 1. SSH User Setup (MVP: SSH Tunnel Path)

### Create Restricted SSH User

Add a new user for phone broadcasts (no shell, port forwarding only):

```bash
# As root on VPS

# Create user
useradd -r -s /usr/sbin/nologin -m -d /var/empty/radiopub radiopub

# Verify
id radiopub
```

### Configure sshd for `radiopub`

Edit `/etc/ssh/sshd_config`:

```bash
# At the end of the file, add:

Match User radiopub
  AllowTcpForwarding local
  PermitTTY no
  X11Forwarding no
  PasswordAuthentication no
  PubkeyAuthentication yes
  PermitOpen 127.0.0.1:1935
  ForceCommand /usr/sbin/nologin
```

**Explanation:**
- `AllowTcpForwarding local`: Allows `-L` local forwarding (to VPS loopback), not `-R` reverse forwarding
- `PermitOpen 127.0.0.1:1935`: Restricts forwarding to the nginx-rtmp ingest port only
- `ForceCommand /usr/sbin/nologin`: Forbids shell login even if the key is used elsewhere
- `PubkeyAuthentication yes`: Requires public key auth; passwords disabled for this user

### Reload sshd

```bash
systemctl reload ssh
# or
systemctl reload sshd
```

### Add Phone Public Keys

Each phone gets one Ed25519 key (generated by the app and stored in Android Keystore).

**Option A: One key per broadcast event** (recommended)
- Operator receives public key from phone (via secure channel or in-app export)
- Add key to `~radiopub/.ssh/authorized_keys` with `restrict` prefix:

```bash
restrict,port-forwarding,permitopen="127.0.0.1:1935" ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIGxyz... event-1-phone
restrict,port-forwarding,permitopen="127.0.0.1:1935" ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAIHabc... event-1-backup
```

**Option B: One key per phone** (simpler, less secure)
- Phone registers key once; reused for all broadcasts
- Add key with same restrictions

**Revoke a key:**
- Delete the line from `~radiopub/.ssh/authorized_keys`
- Active tunnel closes on next reconnect attempt (within ~30 s)

### Test SSH Access

From a test client (or phone emulator):

```bash
ssh -i <phone_private_key> -L 127.0.0.1:1935:127.0.0.1:1935 \
    radiopub@<vps_host> -N &
# Should succeed; connection stays open, no shell prompt

# In another terminal, test publish:
ffmpeg -f lavfi -i sine=f=1000:d=5 -c:a libmp3lame -q:a 9 -f rtp rtp://127.0.0.1:1935/live/test

# Or RTMP:
ffmpeg -f lavfi -i testsrc=size=320x240:duration=5 -f flv rtmp://127.0.0.1:1935/live/test
```

## 2. Control Plane: Invite Code Management

(Post-MVP; in MVP, invite codes may be hard-coded or minted manually.)

### Create an Invite Code

An invite code is an opaque, random token pre-generated for one event.

```bash
# Option A: Using control-plane CLI (if available)
control-plane create-invite \
  --event-name "2026-11-17 Evening Service" \
  --expires-in 24h \
  --max-uses unlimited

# Output: f3a7c2d8a1e6b9f4c5d2e8a1b6c9f4d8 (hex, 256-bit)

# Option B: Manual generation (shell)
openssl rand -hex 32 > /tmp/invite_code.txt
cat /tmp/invite_code.txt
```

### Store Invite Code

- **Development:** Hard-code in control-plane config or display in operator UI
- **Production:** Store in a secure DB (PostgreSQL, Redis, or Vault-like service)
  - Include: event name, creation time, expiry time, usage count
  - Track: which stream names were created under this invite

### Share Invite Code with Operator

- In-person handoff (print, QR code)
- Encrypted email or messaging
- In-app (app shows a PIN or code after login; operator types it or scans)

**Never:**
- Store in plain text in version control
- Send via unencrypted email
- Log it to publicly accessible logs

### Revoke an Invite Code

```bash
# Mark as expired in control-plane DB
control-plane revoke-invite f3a7c2d8a1e6b9f4c5d2e8a1b6c9f4d8

# Result: New POST /v1/control/sessions with this code → 401
# Active sessions created with this code remain valid (credential TTL unchanged)
```

### Invite Lifecycle

| Action | Trigger | Result |
|---|---|---|
| **Create** | Operator (before event) | Code valid, no sessions yet |
| **Use** | Phone creates session | Session recorded, credential minted |
| **Refresh** | Phone calls refresh (before expiry) | Credential renewed, TTL extended |
| **Expire** | TTL reached or revoked | No new sessions; existing sessions remain valid until their own TTL |
| **Cleanup** | Operator or automatic | Delete old expired invites (after 30 days, for audit trail) |

## 4. Troubleshooting

### Problem: "Permission denied" on SSH tunnel creation

**Symptoms:**
```
Permission denied (publickey).
```

**Causes:**
1. Phone's public key not in `~radiopub/.ssh/authorized_keys`
2. Key is revoked (line deleted)
3. sshd config missing `Match User radiopub` block
4. `PermitOpen` restriction doesn't match the tunnel target (127.0.0.1:1935)

**Fix:**
```bash
# Verify key is present
grep "ssh-ed25519" ~radiopub/.ssh/authorized_keys | wc -l

# Check sshd config
sshd -T | grep -A5 "match user radiopub"

# Restart sshd
systemctl restart ssh

# Test with verbose logging
ssh -vvv -i <key> -L 127.0.0.1:1935:127.0.0.1:1935 radiopub@<host>
```

### Problem: "409 Stream name already in use"

**Symptoms:**
```json
{ "code": "stream_name_taken", "message": "Stream 'zenterpres' already in use" }
```

**Causes:**
1. A previous broadcast didn't end cleanly (session still active in control plane)
2. A second phone tried to use the same stream name simultaneously
3. Control plane DB has stale session entry

**Fix:**
```bash
# Option A: End the old session (if you know the sessionId)
curl -X DELETE -H "X-Admin-Key: <key>" \
  https://api.example.church/v1/control/sessions/<old_sessionId>

# Option B: Force expire the session in control-plane DB
# (implementation-dependent; e.g., PostgreSQL)
UPDATE sessions SET ended_at = NOW() WHERE stream_name = 'zenterpres' AND ended_at IS NULL;

# Option C: Use a different stream name for this broadcast
# (operator picks a new stream name and re-authorizes)
```

### Problem: RTMP publish fails ("400 Bad Request")

**Symptoms:**
```
RTMP connect failed: 400 Bad Request / RTMP handshake failed
```

**Causes:**
1. Stream name doesn't match regex `^[a-z0-9_-]{1,32}$`
2. nginx-rtmp is not listening (check container status)
3. SSH tunnel is not established or is closed

**Fix:**
```bash
# Check nginx-rtmp status
docker ps | grep nginx

# Check nginx logs
docker logs web-radio-relay-nginx | tail -20

# Verify tunnel is open
ss -tnp | grep 1935
# Should show: 127.0.0.1:1935 listening

# Test publish locally (from VPS shell)
ffmpeg -f lavfi -i sine=f=1000:d=5 -c:a libmp3lame -q:a 9 -f flv rtmp://127.0.0.1:1935/live/test
```

### Problem: HLS not playing for listeners

**Symptoms:**
```
404 Not Found on https://relay.example.church/live/zenterpres/index.m3u8
```

**Causes:**
1. RTMP stream not reaching nginx (check above)
2. ffmpeg process failed to start (on-publish.sh error)
3. HLS output directory not writable

**Fix:**
```bash
# Check relay API
curl -s https://relay.example.church/api/v1/streams/zenterpres/lifecycle | jq .

# If status is "idle" or missing:
docker logs web-radio-relay-api | grep zenterpres

# Check HLS directory (if accessible)
ls -la /var/lib/web-radio-relay/hls/zenterpres/
```

### Problem: Tunnel closes after 30 seconds

**Symptoms:**
```
RTMP connection closed unexpectedly
ssh_exchange_identification: Connection closed by remote host
```

**Causes:**
1. sshd killed the connection due to `ForceCommand /usr/sbin/nologin`
2. Phone's `TunnelTransport` reconnect kicked in (normal; should auto-retry)
3. sshd has a timeout (unlikely with `-N` flag)

**Fix:**
- Normal reconnect behavior; app should retry with backoff
- Check phone logs for the reason
- If loops continuously, verify SSH key and server config

## 5. Scaling to Multiple Concurrent Broadcasts

### Session Isolation

The control plane enforces **one active session per stream name**. Multiple phones can broadcast if they use different stream names.

```bash
# Scenario: Two services simultaneously (same church, different venues)
# Phone 1 invite: "Event A" → mints stream name "event-a-main"
# Phone 2 invite: "Event B" → mints stream name "event-b-chapel"

# Both streams are independent:
# - RTMP ingest: both enter nginx-rtmp
# - Relay: both pull via MediaMTX (or ffmpeg from nginx)
# - HLS: two separate playlists
# - Archive: two separate MP3 files
```

### Credential Refresh for Long Broadcasts

If a broadcast runs > credential TTL (default 2 hours):

```bash
# At credential expiry – 5 min, phone calls:
POST /v1/control/sessions/{sessionId}/refresh
  Authorization: X-Invite-Code: <same_invite_code>

# Response:
# {
#   "publishCredential": "<new_credential>",
#   "expiresAt": "2026-11-13T12:00:00Z",
#   ...
# }

# Phone updates RTMP credential and continues publishing
# No stream interruption (same session ID, same stream name)
```

### Session Cleanup

```bash
# Automatic (control plane, post-MVP):
# - Mark session as ended if credential expires and no refresh for > TTL
# - Remove ended sessions from active list (keep in audit log for 30 days)

# Manual (operator):
curl -X DELETE -H "X-Admin-Key: <key>" \
  https://api.example.church/v1/control/sessions/<sessionId>
```

## 6. Post-MVP: MediaMTX Integration

Once MediaMTX is deployed on the VPS (planned):

### Update field-radio-control Config

```yaml
# field-radio-control config
mediaUrl: rtmps://media.example.church/live
mediaJwtSecret: <secret_key>
mediaJwtExpiry: 7200  # seconds

relayUrl: https://relay.example.church/api/v1
relayApiToken: <admin_token>
```

### Generate JWT Credentials

```bash
# control-plane now mints JWT instead of opaque strings

# Example JWT payload:
{
  "exp": 1698240000,
  "iat": 1698228000,
  "sub": "session-uuid",
  "iss": "field-radio-control",
  "mediamtx_permissions": [
    {
      "action": "publish",
      "path": "zenterpres"
    }
  ]
}
# Signed with control-plane private key; verified by MediaMTX with public key
```

### Update Phone Publish

Phone publishes to public MediaMTX RTMPS endpoint:

```
publishUrl: rtmps://media.example.church/live
publishCredential: <JWT>
```

### Relay Integration

Relay config updated to pull from MediaMTX instead of nginx:

```bash
# relay config
RADIO_SOURCE_URL_TEMPLATE: rtsp://mediamtx:8554/{name}
```

Now relay pulls stream from MediaMTX → HLS for listeners.

## 7. Security Checklist

- [ ] sshd configured with `Match User radiopub` restrictions
- [ ] PermitOpen limited to 127.0.0.1:1935 only
- [ ] Phone public keys are Ed25519 (not RSA; not weak)
- [ ] No password auth for radiopub user
- [ ] Invite codes are random, >= 256 bits
- [ ] Invite codes never logged in plain text
- [ ] Control plane stores `RELAY_API_TOKEN` securely (env var or vault)
- [ ] JWT signing keys are rotated periodically (post-MVP)
- [ ] Stream name validation enforced both client and server
- [ ] Broadcast session automatically ends when credential expires
- [ ] Old invite codes are cleaned up (after 30+ days)
